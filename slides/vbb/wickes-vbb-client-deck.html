The VBB Opportunity

From volume to value

Standard conversion tracking tells Google Ads that all conversions are equal. Value-Based Bidding tells the algorithm how much each conversion is worth — so it spends more to win the customers that generate disproportionate long-term revenue.

  • Reduce waste on low-value segments — bid less for users unlikely to return or spend further

Concepts

How Value-Based Bidding Actually Works — Two Separate Models

A common misconception is that pCLV is fed directly into Google's auction engine in real time. It isn't. VBB works through two distinct systems that operate at different moments.

Model 1 — Your value label (at conversion time)

When: At the moment a conversion happens (checkout, lead form, trade account signup).

What you send: A numeric conversion_value attached to that specific conversion event via sGTM → Google Ads CAPI.

What it can be: Transaction revenue, gross margin, Acquia pCLV score, or a tier-mapped value (Gold = £200).

What it is NOT: A live bid instruction. Google does not re-run your Acquia or Vertex model at auction time.

Role: outcome labelling You are teaching Google: "conversions that look like this were worth £X to our business."
Model 2 — Google Smart Bidding (at auction time)

When: Every time your ad is eligible to appear in an auction — before any conversion has happened.

What Google uses: Historical conversion values you reported, plus Google's own real-time signals: query, device, location, time, audience lists, remarketing membership, and cross-session behaviour (where permitted).

What it does: Predicts whether this click is likely to produce a high-value conversion, and sets the bid accordingly.

Role: bid optimisation Google's model already integrates browser and auction-time behaviour. What it cannot infer is your offline CRM data, trade account value, or long-term margin logic.
Question Answer
Why send pCLV at conversion time? Because that's the only moment you can attach an accurate value label to a confirmed outcome. Google stores this label and uses it as training feedback for future auctions.
Does Google re-run your pCLV model when bidding? No. Google learns statistical associations: "traffic patterns like this historically produced high reported values." Your model defines the label; Google's model learns when to bid up.
How "recent" must the prediction be? Accurate at conversion labelling time — not millisecond-fresh at auction time. A score updated daily in Acquia and looked up at checkout is usually sufficient. Staleness only matters if a customer's tier changes frequently and you miss that at label time.
Is skipping Vertex AI safe? Yes, for strategic customer-level value. Google already handles session/auction behaviour internally. Acquia's advantage is CRM, offline, and trade-account data Google never sees — not sub-second browser signals.
Implication for Wickes Sending Acquia pCLV at conversion time is not about real-time bid steering — it is about giving Google a richer definition of "value" that incorporates offline sales, trade accounts, and margin logic. That is the gap Google's own model cannot fill, regardless of Phoebe.
Concepts

What Phoebe Actually Does — and What It Doesn't

Phoebe is often misunderstood. It is not a Google proprietary prediction engine that ingests secret browser signals. It is plumbing: an sGTM variable template that calls your own model hosted in Vertex AI, with features you configure.

What Phoebe sends to Vertex AI
  • Event data from the current session — basket items, transaction value, product categories, quantities (from the GTM data layer)
  • Optionally: Firestore profile data — via Artemis (purchase history, segment membership)
  • Optionally: reCAPTCHA score — via Cerberus (bot/fraud signal)
  • Any custom fields you map — in the Phoebe "Request Data" table in sGTM

Not included: Google's auction-time signals, cross-site browsing graphs, or any Google-proprietary data. Those stay inside Google's Smart Bidding model and are never exposed to Phoebe.

Question answered "How valuable is this customer long-term?" "How valuable is this specific conversion event right now?"

Could Acquia be "weaker" than Phoebe for session behaviour? Possibly — if Acquia's model doesn't weight current-session basket context heavily. But Google Smart Bidding already captures much of that session signal at auction time independently. The bigger gap is strategic business value (offline, trade, margin) — where Acquia is likely stronger, not weaker.
Verdict for Wickes Phoebe is not redundant because Acquia is "better at everything." It is redundant because Wickes already has a prediction engine, and the incremental gain from a second session-level Vertex model is small relative to the MLOps cost — especially since Google already handles auction-time behaviour. Use Acquia for what Google cannot see.
Architecture

Standard Pantheon Tools vs. Your Situation

Google's open-source sGTM Pantheon framework offers two standard routes to VBB. Neither maps cleanly to Wickes' situation because Acquia already holds strategic customer-level predictions — the main gap Google cannot fill on its own.

Pantheon Route 1: Phoebe (Vertex AI)

Designed for: Clients with no existing prediction infrastructure who want session-level value scoring. Phoebe calls your own Vertex AI model using event data you configure (basket items, session context, optional Firestore profile).

Why it doesn't fit Wickes: Acquia already answers the strategic value question with richer CRM/offline data. A new Vertex model would mostly re-predict session context that Google Smart Bidding already handles at auction time — adding MLOps cost for marginal gain.

Verdict: Low marginal value Not because Acquia is universally stronger — but because the incremental session-level signal Phoebe would add overlaps with what Google already models internally.
Pantheon Route 2: Artemis + Firestore

Designed for: Clients with pre-computed scores that need ultra-fast (<5ms) lookup at conversion time. Artemis reads from Google Firestore, which receives regular exports of value scores from the source system.

Why it doesn't fit Wickes cleanly: Using Artemis requires building a new data sync pipeline from Acquia to Firestore, duplicating profile data across two platforms, and accepting data freshness lag equal to the export interval.

Verdict: Over-engineered for this case Valid as a high-volume fallback, but introduces unnecessary complexity when Acquia already has a live API.
The adapted approach: Artemis-inspired custom lookup against Acquia's own API Since Acquia exposes a Real-Time Profile API, we can build a custom sGTM Variable Template that queries Acquia directly at conversion time — eliminating the Firestore sync pipeline while preserving the same Soteria value-injection pattern. The key feasibility question is API latency.

Route decision: the latency test

Whether we use Option A or default to Option B depends on a single benchmark: can Acquia's Profile API respond within 150ms at P95 under production load?

Is Acquia Profile API P95 latency < 150ms under production load?
Yes

Proceed with Option A — Direct sGTM → Acquia API. Build custom Variable Template with 150ms timeout and Soteria injection.

No / Uncertain

Fall back to Option B — build Acquia→Firestore export pipeline and use Artemis for sub-ms lookup.

Additional gates

  • API accessibility — Acquia endpoint reachable from sGTM container egress IP without VPN
  • Authentication method — 360 Profile User service account; bearer token via HTTP Basic Auth

Appendix A1

Acquia CDP 360 Profile API — Reference

For Option A (Direct sGTM → Acquia), we propose Acquia CDP's 360 Profile API — the downstream read API for unified customer profiles. This is distinct from the Tracker API (upstream ingest) and WebTag (browser pixel).

What it is / isn't

360 Profile API Read unified profiles — search or direct GET by customer ID. Returns customersummary including predictive analytics and custom calculations.
Tracker API Push events into CDP. Not used for VBB value lookup.
WebTag Browser-side capture pixel. Not used for server-side VBB.
Official precedent Acquia documents real-time 360 API lookups for call-center and CRM embedding — the same pattern as sGTM lookup at conversion time.
