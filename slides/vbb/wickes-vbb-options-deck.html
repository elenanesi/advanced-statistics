Value-Based Bidding · Options Review

Activating Your
Acquia Predictions
in Google Ads

A summary of the architectural routes available to connect your existing customer value scores to Google Ads Smart Bidding — with the trade-offs you need to decide between.

Context

What You Are Trying to Achieve

You already have the core building blocks in place. This project is about connecting them — not rebuilding them.

Acquia CDP

Your customer profiles already include predicted value scores — pCLV, tiers, or similar — built from online and offline data.

Server-Side GTM

Your sGTM container already receives conversion events and forwards them to Google Ads via the Conversion API.

Google Ads

Your campaigns use Smart Bidding. Today, conversions are likely reported with a flat or revenue-based value — not your strategic customer value.

The gap When a customer converts on your site, Google Ads does not yet know how valuable that customer is according to Acquia. Value-Based Bidding closes that gap by attaching your pCLV score to each conversion event, so Smart Bidding can prioritise the customers worth more to your business.

Scope of this document: Three viable routes to make that connection. Each differs in complexity, cost, data freshness, and operational risk. The right choice depends on your Acquia API performance, conversion volumes, and tolerance for additional infrastructure.

How it works

What Happens at Conversion Time

Regardless of which option you choose, the end result is the same: a dynamic conversion value sent to Google Ads when a conversion occurs.

The flow (all options)

Customer converts → sGTM receives event → Value looked up → Sent to Google Ads

The difference between options is where the value is looked up — directly from Acquia, from a Google Firestore cache, or from a new Vertex AI model.

Important: this is not real-time bid steering

You are not telling Google how much to bid in the moment. You are labelling each conversion with a value score. Google's Smart Bidding algorithm learns from those labels over time and adjusts future bids accordingly — combining them with its own signals (device, query, audience, etc.).

What your pCLV score adds that Google cannot see alone

  • Offline store purchase history linked to the customer
  • Trade account status and long-term revenue potential
  • Margin-aware or milestone-based value (e.g. a quote request from a high-LTV segment)
  • Cross-channel behaviour stitched in Acquia's identity graph
Why Acquia scores matter Google already models session and auction-time behaviour internally. Your Acquia pCLV fills the gap for strategic business value that lives outside the browser.

Option A

Direct sGTM → Acquia API  Recommended

When a conversion fires, your sGTM server container calls Acquia's 360 Profile API, retrieves the customer's pCLV score, and attaches it to the Google Ads conversion tag before sending.

Conversion event → sGTM custom variable → Acquia 360 Profile API → Google Ads CAPI
Advantages
  • No additional data pipelines or sync jobs to build or maintain
  • No duplication of customer data across platforms
  • Values always reflect Acquia's latest computed score
  • API credentials stay server-side in sGTM — never exposed to the browser
  • Fastest path to implementation (~2–3 weeks)
  • Uses Acquia's officially documented real-time profile lookup API
Trade-offs
  • Acquia API becomes a runtime dependency on every conversion — must handle timeouts and errors gracefully
  • API latency is not published by Acquia; must be load-tested before committing
  • Email-based lookup may require two API calls (search + profile), adding latency
  • Hashed email search is not documented — a stable customer ID (e.g. SourceCustomerNumber) is preferable
  • Exposes your Acquia API to conversion-volume traffic spikes
InfrastructureNone beyond existing Acquia + sGTM
Implementation~2–3 weeks
Ongoing opsAPI monitoring + token management
Option B

Acquia → Google Firestore → Artemis  High-volume fallback

Acquia has no direct Firestore export. Scores reach Firestore via cloud storage (or Snowflake) plus a custom GCP load job. At conversion, Artemis reads Firestore — not Acquia. See the next slide for official export paths.

Offline — Acquia export → GCS → Firestore
Acquia CDP → Cloud Data Export → GCS bucket → Firestore

Custom GCP ingest (Cloud Function / Dataflow) — not provided by Acquia

Online — per conversion
Conversion event → Artemis lookup → Google Ads CAPI
Advantages
  • Lookup latency is negligible (<5ms) — no risk of slow API blocking conversions
  • Battle-tested Google Pantheon pattern (Artemis + Soteria)
  • No Acquia API rate-limit exposure during traffic spikes
  • Firestore is GCP-managed with a 99.99% availability SLA
Trade-offs
  • Requires building and maintaining an Acquia-to-Firestore export pipeline
  • Customer value data duplicated across two platforms
  • Scores may be stale — freshness depends on export frequency (hours to days)
  • Additional GCP Firestore storage and compute cost
  • Longer implementation (~5–7 weeks)
InfrastructureFirestore + export pipeline
Implementation~5–7 weeks
Ongoing opsSync monitoring + Firestore costs
When to choose Option B If your Acquia API cannot reliably respond within 150ms under production load, or if monthly conversion volume would exceed Acquia API rate limits during peak periods.

Option C

Vertex AI via Phoebe  Not recommended

Google's Pantheon framework includes Phoebe — a template that calls a custom ML model in Vertex AI at conversion time, using session data (basket contents, products viewed) to predict a value score on the fly.

What Phoebe actually does

Phoebe is plumbing to your own Vertex AI model — not a Google proprietary prediction engine. It sends session and event data you configure (cart items, transaction value, optional profile data) and returns a predicted conversion value.

Why this is a poor fit for Wickes

  • Acquia already computes pCLV with richer data (offline, trade accounts, CRM) than a session-level Vertex model could access
  • Google Smart Bidding already models session and auction-time behaviour internally — Phoebe would largely duplicate that signal
  • Requires building, training, and maintaining a new ML model and feature pipeline in Vertex AI
  • Highest implementation effort and ongoing MLOps cost of all three options
When it would make sense
  • If you had no pre-computed value scores anywhere in your stack
  • If session-level prediction (this specific basket, this visit) mattered more than long-term customer value
  • If you wanted full control over the prediction model and features
Trade-offs for your situation
  • Duplicates Acquia's existing ML investment
  • Vertex AI hosting + MLOps overhead on top of Acquia costs
  • Session features overlap with what Google already models at auction time
  • Does not leverage your offline or trade-account data advantage

Recommendation

Suggested Path Forward

Start with Option A — validate with a latency test before committing Option A is the simplest route and makes full use of the pCLV scores you have already built in Acquia. The only gate is whether your 360 Profile API can respond fast enough during live conversions. A short load test answers this definitively.

Decision flow

Can Acquia 360 API respond in <150ms at P95 under production load?
Yes

Proceed with Option A. Build the sGTM custom variable, configure Soteria value injection, and stage on a subset of campaigns.

No / uncertain

Move to Option B. Build the Acquia-to-Firestore export pipeline and use the native Artemis lookup template.

Option C is not on the critical path given your existing Acquia predictions.

Regardless of option — design principles

  • Never drop a conversion signal. If the value lookup fails, fire the tag with a configured default value. Losing the conversion event is worse than sending an un-enriched one.
  • Cap extreme values. Apply a maximum conversion value ceiling to prevent a single outlier score from distorting Smart Bidding.
  • Handle anonymous users. Users without a resolvable identity receive a category-average default value.
  • Monitor fallback rate. Track how often the API fails or times out — a rising fallback rate is an early warning to switch to Option B.
Next steps

What You Need to Confirm Before Implementation

The following items are on your side to resolve. Most can be answered in a single technical session with your Acquia and data engineering teams.

Critical path (blocks Option A scoping)

  • Confirm your Acquia 360 Profile API endpoint URL and provision a 360 Profile User service account for sGTM
  • Confirm the exact attribute key for your pCLV score in the customersummary response (e.g. a custom calculation field name)
  • Run or share a load test of API P50/P95 latency from infrastructure equivalent to your sGTM container
  • Confirm which customer identifier is available in your data layer at conversion time — customer ID, plaintext email, or hashed email only
  • Agree the tier-to-value mapping if scores are categorical (e.g. Gold = £200, Silver = £100)

Also required before go-live

  • Confirm Google Ads campaigns are on Target ROAS or Max Conversion Value bidding
  • Confirm Enhanced Conversions and CAPI are active in your sGTM container
  • Complete GDPR / data governance review for using pCLV in automated ad bidding (Art. 22)
  • Define which conversion events carry dynamic value (checkout, trade account, quote request, etc.)
  • Agree a fallback default value and maximum value cap for the Soteria injection logic
